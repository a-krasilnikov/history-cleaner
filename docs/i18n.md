# Adding a language

Everything user-visible lives in `_locales/<code>/messages.json`. A language is
a folder, not a code change. This file is the only place that carries
per-language knowledge — README, the PRD and CLAUDE.md deliberately don't list
which languages ship, because `ls _locales` already answers that and prose
copies of it can only go stale.

## The procedure

1. Copy `_locales/en/messages.json` into `_locales/<code>/`.
2. Translate the `message` values. Leave the keys, the `$PLACEHOLDERS$` and the
   `description` fields alone — translations drop the `description` fields
   entirely, they are notes for translators, not shipped copy.
3. Cover every plural category the language needs (below).
4. Write `store/description.<code>.txt` for the Web Store listing.
5. `node --test`. The suite fails on a missing key, a missing plural form, a
   dropped placeholder or an English fallback in `options.html` that drifted.
6. If the language taught you something, add it below. That is the whole
   documentation cost of a language; nothing else should need editing.

`npm run pack` already archives `_locales` whole.

## Choosing `<code>`

`<code>` has to be a row of Chrome's own locale table (chrome.i18n reference →
"Locales"). A folder Chrome doesn't recognize is **skipped without an error** —
no warning, no failed load, just an English UI. Verify the code before writing
a translation, not after.

Folder names use Chrome's underscore form (`pt_BR`, never `pt-BR`). That string
is *not* a valid BCP-47 tag: `new Intl.PluralRules("pt_BR")` throws a
`RangeError`, so anything building an `Intl` object from a folder name has to
convert first — `bcp47()` in `test/i18n.test.js`. At runtime the problem never
arises; `chrome.i18n.getUILanguage()` already returns the hyphenated tag.

A regional row usually falls back into the bare code — `es_419` into `es`,
`de_AT` into `de` — so one folder covers a language's variants.

**Portuguese is the exception.** There is no plain `pt` row — only `pt_BR` and
`pt_PT` — and neither falls back to the other, so shipping one leaves the
other's users on the English default. (A bare `pt` folder does reach both at
runtime, through the region-stripping step of the lookup, but the Web Store
ignores it: the listing then can't be translated and the extension isn't shown
as available in Portuguese.)

**Norwegian is unresolved.** The documented table says `no`, while Chromium's
own UI-locale list uses `nb`. Load the extension unpacked in a Chrome set to
Norwegian and see which folder wins before anyone writes the copy — the
failure mode is silent.

**Icelandic (`is`) and Nynorsk (`nn`) aren't in the table at all** and can't be
shipped as locales today.

## Plural categories

`tn()` in `options.js` resolves `<key>_one` / `_few` / `_many` / `_other`
through `Intl.PluralRules`. Ask `Intl` for the categories, never guess — the
answer includes ones no human would list, and the test enforces the full set:

```js
new Intl.PluralRules("pt-BR").resolvedOptions().pluralCategories
```

Quirks worth knowing before writing counted strings:

- **`many` is not a spare copy of `other`.** In Spanish and Portuguese it is
  the millions form, where the counted noun takes "de": "1.000.000 **de**
  elementos". French elides it before a vowel: "1 000 000 **d'**éléments"
  but "1 000 000 **de** sites".
- **Russian needs all four forms.** `other` exists for fractions, which the
  counted strings never reach, but the test still demands it.
- **French `one` also covers zero** — French keeps the singular there. Zero
  never reaches the counted strings anyway; the code routes it to
  `statusNothingFound` / `sweepRemovedNothing`.
- If Finnish ever ships: numerals take the partitive singular ("1 kohde",
  "3 kohdetta"), so both forms differ and neither is a plural.

Relative times ("5 minutes ago", "há 5 minutos") come from
`Intl.RelativeTimeFormat`, not from the catalogue. Only "just now" (`justNow`)
is a string.

## Register, per language

The English copy is friendly and addresses the reader. Each language settles
that its own way; these were deliberate:

- **German** — impersonal throughout ("Zuerst eine Domain eingeben"), which is
  how German UI usually reads and sidesteps du/Sie. The listing description,
  where address is unavoidable, uses Sie.
- **Spanish** — one neutral catalogue for every Spanish-speaking user, so no
  peninsular-only vocabulary.

## Right-to-left

Nothing RTL ships yet. `localizeDocument()` sets `<html dir>` from Chrome's
`@@bidi_dir`, but that covers text direction only. Shipping Arabic, Hebrew or
Persian also means auditing the physical CSS in `options.css` (`margin-left`,
`translateX`, `text-align: right`) into logical properties — a layout task, not
a translation one.

## Cost of a language

Each locale adds four assertions to `test/i18n.test.js` and, more to the point,
one more translation for every future UI string. Chrome falls back per message,
so a partial catalogue is safe — but it produces a half-English screen, which
reads worse than honest English. Add languages you intend to keep.
